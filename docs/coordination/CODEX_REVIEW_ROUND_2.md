## Newly recorded defects

### ROUND2-NEW-001 · HIGH — Calendar paging can exceed the shared cursor limit

`connectors/google_calendar.py:322–339` base64-encodes both tokens and the query state. `backend/app/contracts/sources.py:9,214–220` constrains the result to the 512-character generic key. A synthetic 771-character cursor made from two 260-character tokens was rejected before the next page could run. Use a dedicated larger opaque cursor type with a justified bound, or store paging state separately. Test two full-length opaque tokens through the actual bridge and sync engine. Actual provider token lengths remain unmeasured.

### ROUND2-NEW-002 · HIGH — Calendar 410 recovery leaves stale availability

`connectors/google_calendar.py:439–455` restarts the bounded query after token loss. `backend/app/core/sync.py:144–186` merges it into the previous snapshot without reconciling events absent from the successful replacement. Earlier deleted events can survive in P3 availability. Stage the replacement snapshot and locally retire missing records in the same verified calendar scope after complete, error-free recovery. Preserve historical records and scope a durable token to the matching calendar/query. The existing 410 fixture checks retry, not replacement. [Google Calendar API reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/list)

### ROUND2-NEW-003 · MEDIUM — Drive persists but does not consume its incremental watermark

`connectors/ensora_drive.py:385,449–476` reads modified_since from scope and uses cursor only as a numeric offset. `codex_bridge.py:672–684,743–750` persists the timestamp and sends it back as a cursor without mapping it to modified_since. The next run rescans the folder tree, and the listings exclude trashed items without a deletion reconciliation path (ensora_drive.py:268). Carry separately typed listing and durable tokens and reconcile moved or deleted IDs only after a validated complete scan or authorized change feed.

### ROUND2-NEW-004 · HIGH — Conversion warnings can disclose source content

`codex_bridge.py:699–708` interpolates record ID and exception text before logging. `credentials.py:35–40` removes a small set of recognizable credential forms, but Pydantic errors can echo raw document or academic field values. Return and log constant reason codes, keeping exception text and source identifiers out of default logs. Add a log-capture test with invalid synthetic sensitive fields.

### ROUND2-NEW-005 · HIGH — Local source scope can target the app's own private directories

`backend/app/main.py` accepts a bearer-authorized local folder ID, and `backend/app/core/sync.py:103–116` checks only that a path is present and that source consent is granted. The guarded local open protects the chosen root boundary, but that root may be the application config, secrets or local data directory. Apply a canonical protected-path policy before any local scan or import and add isolated dummy-file tests for private config and data directories. No private user files were inspected.

### ROUND2-NEW-006 · MEDIUM — Explicit diagnostic exports follow destination symlinks

`scripts/p1_sources_cli.py:48–53` opens the destination directly with truncation and chmods the opened inode. An existing symlink would cause the linked file to be overwritten. Use explicit safe replacement in the selected parent directory with an exclusive private temporary file. The independent mode test used a regular disposable file only; the symlink behavior follows from the open flags.
